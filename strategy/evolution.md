# Evolution

Project Kaizen should not begin by building a giant EnterpriseOS.

The sequence should be earned through repeated work.

```text
OPERATORS
↓
REAL TRANSFORMATIONS
↓
RECURRING PATTERNS
↓
METHOD
↓
INTERNAL TOOLS
↓
AUTOMATION
↓
SOFTWARE WHERE JUSTIFIED
```

Services can be the observation and learning engine for later software, but only if repeated patterns actually exist.

## Technology waves

Previous waves become substrate.

Databases, ERP, internet, SaaS, cloud, data platforms, machine learning, generative AI, and whatever comes next each change what is cheaper, faster, or possible.

Persist should repeatedly ask:

> **What just became cheaper, faster, or newly possible, and what does that actually change about this enterprise?**

## Antifragile identity

If one model provider wins, use it.

If open models improve, use them.

If regulation tightens, adapt.

If AI commoditises, the enterprise problem remains.

If robotics or another wave becomes important, absorb it.

> **Do not build expertise around the wave. Build expertise around helping enterprises absorb waves.**

## Apply Kaizen to Persist

Persist is not exempt from its own doctrine.

If diagnosis can be automated, automate it.

If operator work becomes software, consider software.

If a business model becomes obsolete, change it.

If the current method stops working, kill it.

The company must not become attached to the method that currently makes it money.
