# Capability Network

Persist should not permanently employ every possible specialist merely so it can claim to solve every possible problem.

## Core versus network

Persist's core should own:

```text
enterprise understanding
diagnosis
client relationship
orchestration
quality control
measurement
learning
```

Variable specialist depth can come from a trusted network when needed.

## Routing

```text
DIAGNOSIS
↓
CAPABILITY REQUIRED
↓
ROUTE
├── internal team
├── specialist
├── partner
├── vendor
└── temporary operator pod
↓
DEPLOY
```

## Capability graph

Track specialists and partners by attributes such as:

- capability
- industry experience
- geography and jurisdiction
- security or compliance requirements
- cost
- availability
- reliability
- working style
- prior deployment outcomes

The network should become a learned capability graph, not a generic freelancer directory.

## Hiring principle

> **Do not let your payroll define your diagnosis.**

If a capability becomes repeatedly necessary, strategically important, and economically sensible to own, internalise it.

```text
OBSERVE REPEATED DEMAND
↓
MEASURE IMPORTANCE
↓
ASSESS QUALITY / ECONOMICS
↓
INTERNALISE WHEN JUSTIFIED
```

## Operator pods

A pod should be assembled around the diagnosed problem, not around a predetermined service catalogue.

Examples might combine data, ERP, cyber, operations, AI, privacy, finance, or organisational expertise.

Persist remains accountable for orchestration and quality even when specialist capability is external.
